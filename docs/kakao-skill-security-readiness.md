# 카카오 스킬 보안·운영 준비

## 2026-11-23 팀 프로젝트 시험 기준

- 사용자는 유료 상시 운영 서비스가 아닌 팀 프로젝트이며 예상 사용 규모는 1~30명이라고 밝혔다. 운영 서버·도메인은 미정이다. 현재 Docker와 격리 DB, 임시 Quick Tunnel을 팀 시험·시연에 사용하는 안을 우선으로 삼는다. 이 구성을 상시 운영 환경으로 확정한 것은 아니다.
- 시험 PC에서 Docker와 컨테이너가 실행되는 동안만 인증이 가능하다. 터널 재시작 시 공개 주소가 바뀌므로 스킬 URL을 갱신·배포하고 동작 확인이 필요하다. 사용자 웹은 현재 해당 PC의 localhost에만 바인딩되어 있어 다른 기기에서 직접 접근할 수 없다. 웹의 외부 공개와 실사용 데이터 투입은 별도 설계가 필요하다.
- 2026-11-23 임시 터널에 합성 실패 요청 5건을 순차 전송해 모두 HTTP 200임을 확인했다. 왕복시간은 3709, 68, 70, 66, 62ms였다. 같은 구간의 API·스킬 프록시·터널 컨테이너 로그에 합성 코드, 합성 식별값과 시험 비밀이 그대로 나타나지 않았다. 성공 경로, 웹 프록시·외부 로그 수집기, 전체 오류 경로, 실제 카카오 관측 및 동시 30명 부하는 검증하지 않았다. 제한값의 운영 적합성도 이 결과로 확정할 수 없다.
- 시험 비밀은 Git에서 제외된 로컬 파일과 Compose secrets로 전달한다. 로컬 파일은 암호화 저장소가 아니므로 팀원이 안전하게 접근·교체할 방법을 정해야 하며 비밀값 자체는 기록하지 않는다. 실제 운영 비밀과 시험 비밀은 분리한다.

2026-11-19 기준. 운영 호스트·도메인과 예상 사용자 수는 아직 정해지지 않았다. Docker Compose는 실행 방법이며 공인 DNS, 인증서, 외부 서버 및 운영 환경 자체를 제공하지 않는다. 현재 Quick Tunnel과 로컬 웹은 시험용이다.

## 현재 구현과 준비

- 카카오 코드 기본 유효시간은 300초이며 설정 범위는 30~600초다. 요청 제한은 60초 고정 창에서 발급 주소당 20회, 브라우저당 5회, 스킬 전체 60회, 스킬 주소당 30회, 사용자당 5회다. 순차적으로 검사하므로 앞선 제한에 걸리면 뒤 제한은 계산하지 않는다. 이는 현재 구현값이며 운영 부하를 근거로 확정한 값이 아니다.
- 서버는 `getRemoteAddr()`를 사용한다. 현재 구조에서는 애플리케이션이 사용자·카카오 원본 IP 대신 프록시 주소를 볼 수 있고 여러 사용자가 주소별 한도를 공유할 수 있다. 시험용 Nginx의 IP별 제한도 터널 주소를 공유할 수 있다. 전달 헤더를 클라이언트가 조작할 수 있으므로 무조건 신뢰하지 않는다. 운영 프록시·직접 접근 차단·신뢰할 프록시의 범위와 IP 복원 정책을 함께 설계·검증하기 전에는 주소별 제한을 사용자별 보호라고 취급하지 않는다.
- 만료된 카카오 인증 요청과 카카오 가입·새 브라우저 로그인·PIN 재설정의 멱등성 작업은 만료 후 24시간이 지나면 정리한다. 24시간 이전의 기록과 아직 유효한 재시도는 남긴다. 카카오 요청 제한 기록도 마지막 창 시작 후 24시간이 지나면 정리한다. 기본적으로 서버 시작 1분 후부터 1시간 간격이며 서버 중지 중에는 동작하지 않는다. 삭제 시각은 작업 주기에 따라 늦어질 수 있다. 이 보관 기간은 초기 기준이고 운영 목적·개인정보 정책 검토가 필요하다.
- 새 정리 기능은 작업 트리와 별도 시험 DB에서만 검증했다. 현재 실행 중인 시험 API는 변경 전 이미지이므로 새 코드가 적용되지 않았다. 운영 배포나 기존 시험 환경의 재시작은 수행하지 않았다.

## 시험용 터널의 제한적 검증

- 2026-11-19 실제 시험 API·임시 공개 HTTPS 터널에 합성 입력으로 순차 요청 5회를 전송했다. 모두 HTTP 200이었고, 클라이언트 전체 소요 시간은 3,831 / 65 / 66 / 54 / 61ms였다. 첫 요청은 연결 설정 등을 포함한다. 유효한 인증 코드를 확인하는 성공 경로가 아니며 표본도 적다. 카카오 네트워크나 예상 부하의 5초 이내 달성을 증명하지 않는다.
- 같은 시험 구간의 시험 API·스킬 프록시·터널 컨테이너 로그에서 합성 식별값·코드 및 비밀 헤더 원문이 나타나지 않았다. 웹 프록시, 모든 오류 경로, Docker 외부 수집기 및 실제 운영 로그는 검증하지 않았다. 시험용 스킬 프록시는 접근 로그가 꺼져 있다.
- 카카오는 스킬 서버가 5초 안에 응답하도록 안내한다. [카카오 스킬 가이드](https://kakaobusiness.gitbook.io/main/tool/chatbot/skill_guide/make_skill). 운영 배포 위치와 동시 사용자 수를 정한 뒤 유효한 코드의 성공·실패·재시도, 냉간 연결, 동시 부하에 대해 카카오 측 관측을 포함해 측정한다. 타임아웃·오류율과 p95/p99를 기록하고 목표치는 팀이 정한다.

## 비밀과 교체 시 영향

- 운영 비밀은 개발·시험 값과 분리하고 각 용도별로 다른 값으로 관리한다. 운영 비밀 저장소와 접근자·백업·감사·유출 대응 담당자를 정한다. 로컬 Git 제외 파일은 암호화된 비밀 저장소가 아니다. 값은 문서·채팅·로그에 남기지 않는다.
- 스킬 헤더 비밀을 교체하면 서버와 카카오 관리자센터의 운영·테스트 헤더가 일치해야 한다. 현재 서버는 단일 키만 수용하므로 전환 순간 요청 실패 가능성이 있다. 현재 시험 비밀은 카카오 관리자 화면에서 표시되므로 운영 전에 새로운 운영 전용 값을 사용한다.
- 카카오 HMAC 키를 교체하면 기존 코드·브라우저 증명 및 요청 제한의 HMAC을 찾을 수 없어 진행 중인 인증이 무효화되고 제한 상태가 새로 시작될 수 있다. 새 발급을 일시 중지하고 유효 요청이 끝나도록 대기한 뒤 키를 교체하는 절차를 설계한다. 기존 계정의 봇 식별값 연결 자체는 이 HMAC이 아니다.
- 공통 인증 키는 멱등성 범위·요청 지문·재시도 토큰과 대여 코드 조회·표시에 사용된다. 교체 시 진행 중 인증·로그인 재시도와 기존 대여 코드가 영향을 받는다. 기존 세션·브라우저 토큰은 별도 SHA-256 저장을 사용하므로 키 교체만으로 전부 폐기된다고 가정하지 않는다. 관련 코드와 운영 상황을 포함한 교체·복구 시험이 필요하다.
- NFC 비밀은 서버 검증과 리더 서명이 함께 사용한다. 교체 시 양쪽을 맞춰야 하고 이전 서명의 검증 및 재시도에도 영향을 준다. 기존 키의 이중 검증·무중단 교체 기능은 현재 제공하지 않으므로 대여·반납 처리를 안전하게 중단하고 정리한 뒤 협조하여 전환하는 절차를 검증한다.

## 남은 운영 결정

1. 운영 서버·공인 도메인·TLS·프록시·네트워크 접근 경계 및 허용 Origin을 정한다.
2. 신뢰할 프록시의 전달 헤더 처리와 주소별 제한의 정확성을 검증하고, 실제 트래픽을 바탕으로 제한값을 확정·구현한다.
3. 운영 구성에서 모든 애플리케이션·프록시·수집 로그의 코드·식별값·비밀 노출을 점검하고, 예상 부하에서 응답 시간과 오류율을 측정한다.
4. 비밀 저장소·담당자·교체 시점·일시 중단 및 복구 절차를 결정하고 인증·NFC·멱등성 재시도를 실제 구성에서 검증한다.
