# TagBack 서비스 UI 구현 기록

작성: 2026-10-02. 작업 범위: 모바일 사용자 웹과 공용 키오스크. 관리자 대시보드는 별도 범위로 보류.

갱신: 2026-10-05. 사용자 지시에 따라 대여소는 1곳으로 제한하고 선택 UI는 유지한다. 회원가입에 mock 문자 인증을 추가했다. [변경 상세·연동 계약](mobile-auth-catalog.md).

## 최신 변경

2026-10-06: M03/M04와 계정 관리는 전화번호·SMS·PIN 흐름으로 변경했다. 경로별 동작·확정 정책·복구·브라우저 자동 등록 및 미정 설정은 [PIN 인증 문서](pin-auth.md)를 우선 적용한다. 아래 표의 이전 비밀번호 가입 및 SMS 3분/30초 설명은 당시 구현 기록이다. 키오스크와 대여 조회 흐름은 유지한다.

## 근거의 확인 상태

- [프로젝트 허브](https://app.notion.com/p/Vision-UP-2026-2-42843054db4683a0bec60161e858d095)
- [상세 서비스 이용 순서](https://app.notion.com/p/3e543054db4680c38cbbf36eeb6ced92#3ed43054db4680b993a4e61335113fdb)
- [요구사항](https://app.notion.com/p/3e543054db4680d0b82ac95f9947bded)

연결된 Notion fetch에서 세 문서 모두 404/접근 불가를 반환했다. **원문을 읽거나 원문과의 완전한 일치를 검증하지 못했다.** 사용자에게 브라우저로 열어 달라고 요청했다. 아래 대응표는 사용자가 이번 요청에 제공한 요구사항과 화면 ID의 대응이며, 원문 직접 검증 결과가 아니다.

기존 README·CONTRIBUTING·docs/decisions.md는 확인했다. 실행 코드 없는 초기 저장소였으며 예정된 React + TypeScript + Vite를 사용했다. 실 API 계약이나 NFC 규격을 팀 합의 없이 확정하지 않고 모의 adapter로 격리했다.

## 요구사항과 충돌 처리

1. 사용자의 명시적 지시 → 상세 이용 순서 → 요구사항 데이터/처리 규칙 순서로 적용.
2. 학번 인증 설명과 전화번호·일회성 코드 시나리오 충돌은 병합하지 않는다. 이번 구현은 **웹 전화번호 로그인 → 코드 확인 → 키오스크 입력**이다. 학번만으로 인증하지 않는다.
3. 키오스크가 문서에서 추가 아이디어일 수 있지만 이번 구현의 필수 범위로 취급한다.
4. 스마트폰 NFC 중심의 기존 README 설명과 달리 이번 범위는 현장 키오스크 + 별도 NFC adapter다. 실제 장비 연결 방식은 미정이다.
5. 모바일에서는 탐색·코드·기록 조회만 한다. 대여·반납 확정은 키오스크에서만 가능하다.
6. 반납은 로그인/코드 없이 NFC로 진행 중 기록 조회 → 사용자 상태 확인 → 확정이다.
7. NFC는 실물 식별이며 물품의 실제 회수 완료를 증명하지 않는다.
8. 예약, 결제, 보증금, AI 손상 판정, 배송, 제재 정책은 추가하지 않는다.

## 독립된 흐름

```text
모바일 /mobile
M01 탐색 → M02 상세 → (비회원 M03 로그인 ↔ M04 가입) → M05 코드
                          로그인 성공 시 원래 목적지 복귀
하단 내비게이션: M01 탐색 / M05 코드 / M06 내 대여 / M07 기록
M06 → M07, 계정 화면 → 로그아웃

키오스크 /kiosk
K00 시작 → K01 종류 → K02 코드 → K03 NFC → K04 확인 → 모의 저장 → K05 완료 → K00
K00 시작 → K06 NFC → K07 물품·상태 → K08 확인 → 모의 저장 → K09 완료 → K00
진행 중 이전 / 취소, 무활동 시간 초과 → 세션 삭제 → K00
응답 유실 → 결과 재조회 → 확인된 결과에 따라 완료 또는 동일 요청 재시도
```

키오스크의 현재 단계는 메모리에 보관한다. 새로고침·직접 진입은 시작 화면으로 이동한다. 모바일 라우터·레이아웃·개인 세션을 재사용하지 않는다.

## 처리 규칙 대응

| 사용자 규칙 | 구현 위치 / 검증 근거 |
|---|---|
| 종류와 실물 분리·종류 일치 | `Kind`/`Item`, scan의 kindId 검증, K03 오류 |
| 확정 때 서버 재검사 필요 | mock rent 트랜잭션에서 active/status/kind/station/code 재검사; 운영 서버 구현 필요 |
| 기록+상태 저장 후 완료 | save가 기록·물품·코드를 한 번에 저장; K04/K08 promise 성공 후만 완료 |
| 연타/중복 태그 | 동기 ref 잠금, 태그 디바운스, operationId별 모의 결과 재사용 |
| 결과 불명 안전 복구 | 저장 후 응답 유실 Fault → UNKNOWN → 결과 조회, 같은 operationId 유지 |
| 모바일 데이터 갱신 | 동일 origin storage 이벤트, 포커스 복귀 재조회; 운영 서버 이벤트로 교체 필요 |
| 개인 기록 권한 | mock 세션으로 userId를 유도하여 본인 기록만 반환; 실제 서버 인가 아님 |
| 종료 초기화 | reset이 인증/코드/물품/상태/결과를 제거, 비동기 epoch 무효화 |
| 상태와 연체 분리 | Item: available/rented/inspection, Rental.dueAt으로 연체 계산 |

## 실제 운영 전 남은 범위

실제 본인 확인·서버 로그인·인가·데이터베이스 트랜잭션·서버 멱등성·코드 정책·리더기 transport·실물 회수·다른 기기 간 동기화는 구현되지 않았다. 브라우저 localStorage의 mock 데이터는 실제 서비스 보안/영속성 보장으로 사용하지 않는다. 관리자 기능과 물품 등록·점검/수리 운영은 이번 사용자 UI에 섞지 않고 후속 작업으로 남긴다.

검증 명령·결과는 `frontend/README.md`와 `docs/service-ui-verification.md`를 참고한다.
