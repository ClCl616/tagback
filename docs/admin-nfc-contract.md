## 확인된 계약과 구현 경계

태그 연결은 `POST /api/items/{itemId}/tag`, JSON `{ "uid": "..." }`, 관리자 세션 인증이다. 최초 연결은 201, 같은 물품 ID·같은 정규화 UID 재요청은 기존 태그를 200으로 반환한다. 두 성공 응답은 `{tag:{tagId,uid,itemId,status:"ACTIVE",createdAt}}`. ID는 백엔드 Long이다. UID는 공백/콜론/하이픈 제거 후 대문자이며 16진수 8/14/20자리다. 다른 물품에 연결된 UID는 `409 TAG_ALREADY_REGISTERED`, 같은 물품에 다른 UID를 연결하려면 `409 ITEM_ALREADY_TAGGED`다. 교체/해제는 제공하지 않는다.

`tagTransport.ts`는 확인된 경로/요청/응답/오류만 사용하는 HTTP 함수다. 현재 화면에는 연결하지 않았다. 브라우저 mock UUID를 실제 서버 Long ID로 보내면 안 되며, 물품 생성·목록 계약과 관리자 인증 연결이 먼저 필요하다. 200/201 모두 응답의 물품 ID·정규화 UID·ACTIVE 상태가 일치해야 완료한다. 잘못된 JSON·필드·상태·계약 밖의 2xx는 결과 불명으로 처리한다.

현재 FE는 DEV 전용 관리자와 localStorage mock DB다. `shared/nfc.ts`의 BroadcastChannel 이벤트만 수신하고, 시뮬레이터가 이벤트를 발행한다. 실물 리더기나 Web NFC 연동을 완료한 것으로 간주하지 않는다.

## 이번 FE 구현

- 신규 등록은 정보를 저장한 반환 Item의 ID로 태그를 연결하는 두 단계다. 생성 요청에 UID를 함께 저장하지 않는다.
- 신규 물품은 태그 없이 먼저 저장되고 비활성 상태로 시작한다. 연결 성공 후 활성화한다. 이 규칙은 mock 모델이며 서버 필드를 가정하지 않는다.
- 실패하면 입력 유지. 물품 저장 이후 실패하면 저장된 ID 유지, 정보 입력 잠금, 태그만 재시도한다. 확정된 오류 이후에는 새 UID를 인식할 수 있지만, 통신 오류/응답 유실이면 결과가 확인될 때까지 같은 UID를 유지한다.
- 목록/상세에 `태그 미등록`을 표시한다. 미등록 물품의 수정 화면에서 NFC를 인식해 연결한다. 정보만 수정하는 것도 가능하다.
- 창을 닫거나 새로고침해도 이미 생성된 미등록 물품은 DB/목록에 남는다. 해당 물품을 선택해 이어간다.
- 중복 제출은 UI 비활성화와 동기식 in-flight 가드 양쪽에서 방지한다.
- 태그 연결 응답 유실/네트워크 실패는 저장된 물품 ID·정규화 UID로 같은 POST를 재요청한다. 이미 연결되었다면 200, 연결 전 실패였다면 201이며 두 경우 모두 검증 후 완료한다. 태그 조회 API를 호출하거나 가정하지 않는다. 재시도는 물품 생성/수정을 다시 수행하지 않으며, 다른 UID 충돌은 오류로 남긴다.
- 물품 생성 응답 유실은 별개다. 물품 ID를 아직 모르면 태그 연결의 재시도 안전성을 적용할 수 없다. 현재 mock만 operation UUID 조회를 사용하며, 생성 결과 확인도 실패하면 재생성을 차단한다.
- 모의 생성 결과 조회는 클라이언트 operation UUID에 해당하는 로컬 DB 행을 찾는다. **이것은 서버의 idempotency나 조회 API가 아니다.** 실제 서버에서 같은 보장을 제공하려면 아래 계약이 필요하다.
- 새 성공 배너는 없으며, UID를 입력한 신규 등록 창은 두 단계가 모두 완료된 뒤에만 닫는다. UID 없이 등록하면 물품 생성 완료 후 닫는다. 부분 성공은 창에 별도로 표시한다.

## 백엔드/리더기 협의 필요

1. **물품 생성 API**: 경로, 요청 필드, 필수값, 이미지 저장 방식, 성공 응답의 물품 ID 위치·타입. 카테고리/이름/관리번호/대여소/상태의 서버 모델 매핑.
2. **생성 응답 유실 확인**: idempotency key 또는 요청 식별자로 생성 결과를 찾는 수단. ID를 받기 전에 연결이 끊겼을 때 목록의 이름 비교만으로 성공을 판단하면 안 된다. 키 수명과 화면 재진입 복구도 합의해야 한다.
3. **물품 목록/상세 및 태그 상태 조회**: 실제 경로와 응답 스키마, 미등록 표현, 연결 UID와 활성 상태, 조회 일관성. 목록/상세 표시에 필요한 계약이며, 태그 POST 재시도의 선행 조건은 아니다. `ITEM_ALREADY_TAGGED`만으로 이번 요청이 성공했다고 판정하지 않는다.
4. **NFC 리더기 전송**: ACR1552U 브리지 transport, 이벤트 형식, 연결/해제/오류 처리, UID 바이트 순서와 실물 테스트. 현재 BroadcastChannel을 실제 하드웨어 계약으로 간주하지 않는다.
5. **인증/배포**: 관리자 세션 발급, FE origin 및 쿠키/CORS/프록시. 현재 관리자 UI는 DEV 전용이며 운영 라우트/인가 완료 범위가 아니다.

이 계약이 없으므로 실제 서버의 전체 등록·상태 확인은 미연결이다. 임의의 생성/조회 URL이나 응답 필드를 추가하지 않았다.

## 검증 범위

순서/생성 ID 사용, 기존 물품 후속 연결, 생성 실패 재시도, 태그 실패 재시도, 중복 제출, 생성 응답 유실 및 생성 결과 조회 실패 후 재확인, 태그 응답 유실 후 동일 POST 재요청, 동시 연결 충돌, UID 규칙, 확인된 POST 요청·오류를 테스트한다. 브라우저 테스트는 실제 화면과 mock 저장소의 입력 유지/재접속/상세 반영을 확인한다. HTTP 함수 테스트는 응답 스텁이며 실제 백엔드·DB·실물 NFC 검증이 아니다.

검증 결과: 등록/계약 단위 테스트 16개, 기존 서비스 테스트 20개, 관리자 브라우저 테스트 15개 통과. TypeScript 검사 및 production 빌드 통과. 새 물품 부분 성공 후 창 닫기/새로고침/같은 ID 연결 재개도 추가 검증했다. PC·모바일 편집창 캡처로 기존 배치가 유지되는지 확인했다.

## 태그 없는 선등록 및 상태 제한

2026-10-18: 아래는 DEV mock 동작이다. 서버는 TAG_PENDING으로 생성하고 태그 연결 시 AVAILABLE로 전환한다. 두 구현은 아직 다르며 실제 관리자 API 연동 시 상태 모델과 화면을 서버 계약에 맞춰야 한다. 서버 구현 누락으로 취급하지 않는다.

태그 없이 신규 물품을 등록할 수 있다. 기본 상태는 점검 중이며, 태그 연결을 마친 뒤에만 대여 가능으로 변경할 수 있다. UID를 인식만 한 상태는 연결 완료로 취급하지 않는다. 연결 후 상태를 자동으로 대여 가능으로 바꾸지는 않는다. UI 선택 제한과 mock 저장 검증을 함께 적용하며, 이전 mock 데이터의 태그 미등록/대여 가능 상태도 점검 중으로 이관한다. 실제 서버 연동 시 같은 상태 제약을 서버에서도 강제해야 한다.

## NFC 인식 테스트 시뮬레이터

`/dev/simulator` 상단의 NFC 인식 테스트에서 UID 직접 입력 또는 새 테스트 UID 생성 후 이벤트를 전송할 수 있다. 같은 브라우저·같은 origin의 다른 탭에서 관리자 등록/수정 창 또는 키오스크 NFC 대기 화면을 먼저 연다. UID 형식은 관리자와 공통 검증하며 잘못된 값은 전송하지 않는다. 같은 UID를 다시 보내면 중복 연결 오류를 확인할 수 있다. 전송 표시는 이벤트 발행 결과이며 연결 성공을 의미하지 않는다. 실제 하드웨어가 아닌 BroadcastChannel 테스트다. 태그 없는 물품은 기존 태그 전송 목록에서 제외한다.

검증: 두 브라우저 탭을 이용한 UID 입력/정규화/인식/신규 연결/중복 오류/새 UID 재시도/리더기 설정 해제 시 전송 차단 테스트 통과. 단위 테스트 38개와 TypeScript·빌드 통과.

## 개발 시뮬레이터 물품 데이터 도구

`/dev/simulator`의 물품 Mock 데이터에서 수량 1~500개를 지정해 기존 목록에 추가한다. 브라우저 저장소 보호를 위해 삭제된 행을 포함한 전체 물품은 2,000개로 제한한다. 기존 분류/대여소를 이용해 이름·상태를 무작위로 선택하고 관리번호/ID/UID는 중복되지 않게 생성한다. 태그는 혼합/모두 연결/모두 미등록을 선택할 수 있다. 미등록 물품은 점검 중 또는 수리 중만 허용한다. 대여 기록 없는 대여 중 상태는 생성하지 않는다. 사진은 업로드하지 않고 기본 아이콘을 사용한다.

전체 삭제는 확인 후 items/rentals/operations/codes/grants를 함께 비운다. 계정·인증·분류·카테고리·대여소는 유지한다. 쓰기는 DEV 전용이고 Web Locks 기반 mock 트랜잭션을 사용한다. 같은 origin의 관리자 목록에도 자동 반영된다. 실제 서버 데이터는 변경하지 않는다.

검증: 수량/전체 상한/동시 생성/UID 및 관리번호 중복 방지/상태 제약/삭제 범위 단위 검증 포함 41개 통과. 전체 삭제 취소·확인, 재생성, 관리자 자동 반영, 새로고침 유지, 모바일 가로 넘침 및 NFC 인식 브라우저 테스트 2개 통과. TypeScript·빌드 통과.

## PR #10 최신 재시도 계약 반영

최신 코드 e72bfc2(병합 52fd5c6)의 201/200·두 409 분기를 확인했다. Mock도 물품의 기존 연결을 먼저 검사해 동일 UID는 기존 연결 그대로 반환하고, 다른 UID 또는 다른 물품 UID는 각각 충돌로 처리한다. Web Locks 안에서 검사하므로 동일 연결 동시 요청에도 한 연결만 남는다. 실제 서버 연결은 활성화하지 않았다. 물품 생성 응답 ID·생성 결과 확인/idempotency·이미지·목록/상세·실물 리더기 계약은 후속 사항이다.

최신 반영 검증: 단위 테스트 47개(등록/HTTP 계약 21개, mock 서비스 26개), 관리자·NFC 브라우저 테스트 17개, TypeScript 및 production 빌드 통과. 201 최초 연결/200 동일 연결, 두 409, 응답 유실 후 같은 POST로 완료·물품 생성 1회, UID 잠금, 잘못된 물품 ID/UID/상태/JSON/2xx 거부, 선등록 및 대여 가능 제한을 확인했다. 실제 HTTP 서버·DB·리더기는 검증하지 않았고 서버 연결도 활성화하지 않았다.
