# 전화번호·PIN 인증 구현 — 2026-10-06

첨부 이미지의 전화번호/SMS 화면과 점·키패드 PIN 화면을 참고하되 TagBack 색상과 브랜드를 유지한다. 기존 미커밋 단일 대여소·조회 개선 위에 구현했다. 실제 API/SMS/NFC 연결은 없다.

## 확정 정책

- PIN 숫자 6자리. 앞자리 0 허용. 전체 6자리의 순환 포함 오름/내림차순 금지, 동일 숫자 3자리 이상 연속 금지. 다른 패턴은 추가 제한하지 않는다.
- PIN 실패 계정별 누적: 5회 30초, 10회 1분, 15회 5분, 20회 복구 필요. 대기 종료로 횟수를 지우지 않는다. 정상 로그인·PIN 재설정 완료 시 초기화. 대기 중 검증/실패 추가 누적 없음.
- SMS 6자리, 5분, 재발송 30초, 번호별 오입력 5회 폐기. 성공 후 번호 재사용 금지. 새 SMS 발급 시 같은 전화번호의 모든 용도에서 이전 미검증 인증번호와 미사용 SMS 인증 결과를 폐기한다. 재발송 대기·발송 한도 오류나 동일 요청 ID 재시도에서는 폐기하지 않는다.
- SMS proof를 번호·용도(access/reset/change)·모의 요청 출처에 결합한다. 가입 중 번호 확인은 access, 재설정과 번호 변경은 별도 용도다.
- 활성 브라우저 등록 1개, 세션과 등록 분리. 로그인 성공 시만 이전 등록/세션 폐기. 동일 브라우저 여러 탭은 localStorage 인증 정보 공유.
- 일반 로그아웃은 세션 종료, 등록 유지. 등록 해제는 둘 다 종료. 사용자 화면의 등록 해제 버튼은 후속 요청에 따라 제거했다.
- PIN 재설정·전화번호 변경 후 전체 세션/등록 폐기, 자동 로그인 없음. 내부 user ID와 대여 기록 유지.
- 키오스크 grant와 모바일 인증은 별도. 새 모바일 로그인만으로 기존 키오스크 grant를 폐기하지 않는다.
- 전화번호당 1계정. 실명 확인 또는 1인 1계정 보장이라고 표현하지 않는다.

## 시연용 미정 정책 설정

확정 값은 shared/authPolicy.ts의 AUTH_POLICY, 임시 값은 AUTH_DEMO에 분리했다.

| 항목 | 이번 시연 가정 |
|---|---|
| SMS proof / 재인증 proof | 10분 |
| 모바일 세션 전체 / 무활동 | 24시간 / 30분 |
| 브라우저 등록 | 30일, 로그인 성공 시 새 자격 정보 발급·이전 폐기 |
| 발송량 | 1시간 전화번호 10회 / 모의 출처 30회 |
| SMS 검증 요청 | 1시간 전화번호 30회 / 모의 출처 100회 |
| PIN 검증 요청 | 모의 출처 1시간 100회, 계정별 확정 제한과 별도 |
| 복구 조건 | 등록된 번호의 SMS 인증 성공 |

모든 시간 제한은 mock 서비스가 검증한다. UI 타이머만으로 통과시키지 않는다. 출처 ID는 mock 요청 분류용이며 인증 증거가 아니다. 운영 서버는 실제 요청 출처 정책, 등록 갱신/회전 및 복구 수단을 별도로 설계해야 한다.

## 구조·운영 연동 경계

- shared/authTypes.ts: 교체 가능한 AuthAdapter, 요청 결과와 mock 인증 데이터 타입.
- shared/auth.ts: mock 인증·시도 제한·SMS·등록·세션·복구·인증 작업 결과. API 경로는 추측하지 않았다.
- 실제 HTTP 인증 요청·응답과 mock 필드의 대응은 [인증 API 계약](auth-api-contract.md)을 따른다.
- mobile/AuthFlow.tsx: 전화번호/SMS/PIN/복구/번호 변경 화면 상태. PIN 설정은 URL만으로 우회할 수 없고 저장 시 proof 재검증.
- MobileApp.tsx: 개인 세션 동기화·만료 안내·프로필/내 계정. 탭 이벤트·포커스·30초 재확인, 보호된 조회마다 mock 세션 검증.
- shared/api.ts: 기존 물품·대여 계약 유지. 개인 조회는 새 인증 세션 검증을 이용한다.

모의 저장은 localStorage와 Web Locks를 이용한다. PIN은 신규 설정 시 salt + SHA-256으로만 처리하며 운영 비밀번호 저장 방식의 대체물이 아니다. 기본 시연 계정은 고정 시연 PIN의 SHA-256이다. 실제 서버는 적절한 비밀번호 해시와 안전한 세션 전달/저장·인가·멱등성·발송 제한을 구현해야 한다. 현재 localStorage에는 mock 인증 자격 정보가 있으므로 실제 개인정보/운영 자격 정보를 입력하지 않는다.

등록 자격 정보 자체가 모의 서버에 존재하는지 검사한다. 브라우저 이름이나 전화번호만으로 로그인하지 않는다. 운영에서 등록된 기기 증명을 어떤 인증 수단으로 구현할지는 별도 보안 검토 대상이며, mock 토큰만으로 인증 수준을 보증하지 않는다.

저장 요청의 operation ID는 임의 UUID로 생성하고 모의 조회 권한을 가진 비밀값으로 취급한다. 새로고침 시 sessionStorage에 남은 진행 중 ID로 결과를 확인한다. 화면 이탈 후 늦은 응답은 로그인 상태에 적용하지 않는다. 실제 서버에서는 요청 소유자 검증과 결과 반환 권한이 추가로 필요하다.

DB 키는 유지하고 schemaVersion 3으로 이관한다. 물품·대여·개별 계정 ID·이력은 보존한다. 이전 인증 세션/SMS만 폐기하고 비밀번호 해시를 제거한다.

- 기타 이전 mock 계정은 PIN 미설정 상태로 보존한다. 등록 번호 SMS 확인 후 PIN을 설정한다.
- 운영 비밀번호 계정 전환 기능은 구현하지 않는다.

## 2026-10-06 개인정보 입력·마이페이지 변경

- 신규 가입: 이름·직업 → 전화번호 → SMS 확인 → PIN 설정·재입력 → 가입 저장. 개인정보는 최종 가입 성공 시 계정에 저장하며 인증 없이 가입 API를 호출해도 저장할 수 없다.
- 이름/직업 필수, 앞뒤 공백 제거, 각각 최대 40자. 직업은 Select(학생·직장인·자영업·프리랜서·구직 중·기타)로 선택하며 목록은 현재 UI 구현 가정이다. 직업별 권한이나 가입 제한은 추가하지 않는다.
- 마이페이지는 이름·직업, 본인의 대여 중 수/이용 기록 수, 대여 코드, 계정 관리로 구성한다. 다른 계정 로그인 버튼, 로그인 성공 배너, 마이페이지 등록 해제 버튼과 안내를 제거한다. 일반 로그아웃의 등록 유지 정책은 동일하다. PIN 화면의 등록 해제 버튼도 후속 요청에 따라 제거했다.
- 기본 mock 계정 이름은 김태백, 직업은 학생. 이름 없는 기존 계정은 회원으로 표시하며 기록을 삭제하거나 임의의 실명을 배정하지 않는다. 이름/직업 없는 기존 데이터도 로그인 가능하다.
- 이름/직업은 본인 입력값이며 실명 검증 또는 1인 1계정 보장 수단이 아니다. 실제 연동 전 backend의 signup 요청에 profile.name/profile.occupation, me 응답에 name/occupation 필드를 반영해야 한다.
