# 물품 반출 API 계약

작성: 2026-10-14. 작업 브랜치: `feat/item-checkout`.

현재 상태: 1~4단계 구현. 데이터 접근·반출 서비스·HTTP API·키오스크 코드 인증·멱등 재생을 구현했다.
인증 관련 신규 API는 기존 인증과 동일하게 `sms-mock & !prod & !production` 프로필에서만 제공한다.
사용자는 키오스크 대여 코드 인증과 최초 대여 기간 72시간을 선택했다.
아래 경로·필드·오류는 현재 서버 구현이며 프론트엔드·NFC 담당자와 공유할 연동 계약이다.
팀 합의 완료나 프론트엔드·실물 NFC 연동 완료를 의미하지 않는다.

## 1. 범위와 결정

| 항목 | 이번 결정 |
|---|---|
| 반출 주체 | 키오스크에서 대여 코드를 검증한 사용자 |
| 모바일 역할 | 로그인 후 대여 코드 발급·표시. 모바일 세션만으로 반출을 확정하지 않는다. |
| 대여자 식별 | 서버가 대여 코드와 반출 인증 토큰을 조회하여 결정한다. 요청의 userId·전화번호는 사용하지 않는다. |
| 물품 식별 | NFC 조회로 확인한 개별 물품의 `itemId`. 선택 종류인 `itemTypeId`도 전달하여 확정 시 일치를 재검사한다. |
| 반출 가능 조건 | 태그가 연결된 `AVAILABLE` 물품이며 진행 중 대여가 없어야 한다. |
| 반출 시각 | 서버가 반출 처리 시 정하는 하나의 시각. 클라이언트 시각을 받지 않는다. |
| 반납 예정일 | `dueAt = rentedAt + 72시간`. 자정·영업일 기준으로 보정하지 않는다. |
| 저장 단위 | 대여 이력·물품 상태·상태 변경 이력·코드 사용 처리·재시도 성공 결과를 한 트랜잭션에서 반영한다. |

이번 범위에는 반납, 예정일 연장·변경, 사용자별 대여 조회 API를 포함하지 않는다.
종류별 기간, 휴일 보정, 1인 수량 제한, 연체 이용 제한은 별도 정책이며 이번에 임의로 추가하지 않는다.
단일 대여소를 사용하고 반출 요청에 `stationId`를 받지 않는다. 프론트 표시용 대여소 매핑은 별도 연동 사항이다.

## 2. 인증과 화면 흐름

1. 모바일에서 기존 로그인 세션으로 대여 코드를 발급받는다.
2. 사용자가 키오스크에 코드를 입력하면 서버가 코드를 검증하고 짧은 수명의 반출 전용 토큰을 발급한다.
3. 키오스크에서 NFC로 개별 물품을 조회하고 사용자에게 물품·예정일을 표시한다. 조회만으로 대여를 생성하거나 코드를 소비하지 않는다.
4. 사용자가 반출을 확정하면 반출 전용 토큰과 물품 정보를 전송한다.
5. 서버는 코드·토큰·물품을 다시 검증하고 저장한다. 성공 응답을 확인한 뒤 완료 화면을 표시한다.

대여 코드는 기존 화면의 6자리 숫자·발급 후 3분 규칙을 유지한다. PIN/SMS 인증 코드와는 별도다.
반출 전용 토큰의 만료는 원래 대여 코드 만료를 넘기지 않으며, 검증 반복으로 유효 시간을 늘리지 않는다.
코드 검증 시점에는 소비하지 않고, 반출 저장 성공 시 코드를 소비한다. 같은 코드에서 발급된 다른 토큰도 추가 반출에 사용할 수 없게 한다.

선행 인증 API:

| 작업 | 경로 | 인증·입력 | 성공 응답 |
|---|---|---|---|
| 코드 발급·확인 | `POST /api/v1/rental-codes` | 기존 사용자 세션, Origin 검사, 빈 JSON 객체 | `200 { "code": "123456", "expiresAt": "2026-10-14T03:03:00Z" }` |
| 코드 검증 | `POST /api/v1/kiosk/rental-grants` | `{ "code": "123456" }` | `201 { "token": "opaque", "expiresAt": "2026-10-14T03:03:00Z", "maskedPhoneNumber": "010-****-5678" }` |

코드 발급은 유효한 미사용 코드가 있으면 재사용하고, 만료·사용 후에만 새 코드를 발급한다.
코드 검증은 모바일 로그인 쿠키를 요구하지 않지만, 서버의 코드 검증과 시도 제한을 반드시 거친다.
코드 충돌 방지, 토큰 해시 저장, 발급·검증 제한, 동시 소비 제어를 구현했다.
개발 기본값은 사용자당 신규 코드 1시간 10개, 접속 주소당 코드 검증 1분 10회, 서버 전체 1분 60회다.
`application-sms-mock.properties`의 `tagback.rental.*`로 조정할 수 있다. 운영 수치는 팀과 별도 합의한다.
유효 코드 재표시는 신규 발급 한도에 포함하지 않는다. 코드 검증은 성공·실패 모두 횟수에 포함하며
실패 트랜잭션과 별도로 DB에 기록한다. 검증 제한은 고정된 UTC 분 단위 창을 사용하고 429에 `retryAt`을 반환한다.
접속 주소는 서버의 `getRemoteAddr()`를 사용하며 임의 `X-Forwarded-For`로 우회하지 않는다.
프록시 환경의 실제 주소 전달·신뢰 설정은 배포 환경에서 검토해야 한다.

`RentalAuthenticationInterceptor`가 `@RentalAuthenticated` 요청에서 반출 전용 토큰을 먼저 검증한다.
그 결과가 있는 경우에만 `SessionAuthenticationInterceptor`가 모바일 세션 검사를 생략한다.
인증 서비스가 없으면 요청을 거부한다. 코드 검증 API의 `@PublicApi`는 모바일 세션만 생략하며 코드 검증은 수행한다.
반출 API는 모바일 쿠키를 대신 사용하거나 클라이언트의 Mock `Grant.userId`를 신뢰하지 않는다.
공용 키오스크에 사용자 로그인 쿠키를 복사하지 않는다.

## 3. 반출 요청

```http
POST /api/v1/rentals
Authorization: Bearer <반출 전용 토큰>
Idempotency-Key: <UUID>
Content-Type: application/json

{
  "itemId": "12",
  "itemTypeId": "3"
}
```

| 필드 | 규칙 |
|---|---|
| `itemId` | 필수 JSON 문자열. 양의 BIGINT 범위(1~9223372036854775807)의 10진수, 선행 0 불허 |
| `itemTypeId` | 필수. 같은 ID 형식. 키오스크에서 선택한 종류와 물품의 현재 종류를 비교한다. |
| `Authorization` | 서버가 발급한 반출 전용 토큰. 일반 로그인 토큰이나 요청 userId로 대체할 수 없다. |
| `Idempotency-Key` | 필수 UUID. 한 번의 확정 작업에 하나를 생성하고 응답 유실 시 그대로 재사용한다. |

숫자·불리언을 문자열 ID로 자동 변환하지 않는다. 누락·null·공백·범위 초과·미정의 필드는 `400 INVALID_INPUT`이다.
`userId`, `rentedAt`, `dueAt`, `status`, `stationId`는 요청 필드가 아니며 보내면 거부한다.
인증 정보와 키가 중복된 헤더 등 모호한 자격 정보도 거부하도록 구현한다.

NFC UID의 정규화와 UID→물품 조회는 NFC 조회 계약에서 처리한다. UID와 itemId를 반출 요청에 중복 입력받지 않는다.
현재 서버의 태그 등록 API는 조회 API의 대체물이 아니다. 키오스크용 NFC 조회 인증·경로는 NFC 담당자와 연결해야 한다.
itemId 또는 UID를 전송했다는 사실만으로 실물 접촉·현장 반출을 증명하지는 않는다.

## 4. 성공 응답

최초 생성은 `201 Created`, 동일 요청의 성공 재생은 `200 OK`다. 두 응답의 본문은 같다.
`Cache-Control: no-store`를 적용하며, 아직 구현하지 않은 대여 상세 조회 주소를 Location 헤더로 약속하지 않는다.

```json
{
  "rentalId": "101",
  "itemId": "12",
  "itemTypeId": "3",
  "rentalStatus": "RENTED",
  "itemStatus": "RENTED",
  "rentedAt": "2026-10-14T03:00:00Z",
  "dueAt": "2026-10-17T03:00:00Z",
  "returnedAt": null
}
```

ID는 문자열, 상태는 서버 enum의 대문자, 시각은 UTC ISO 8601 문자열이다.
한국 시간 표시로는 위 예시가 10월 14일 12:00 반출, 10월 17일 12:00 반납 예정이다.
DB에는 시차를 포함하는 시각으로 저장한다. 화면의 확정 전 예정일은 예상값이며, 성공 응답의 `dueAt`을 최종값으로 사용한다.
반납 예정일 변경 정책이 나중에 추가되어도 기존 대여의 저장된 `due_at`을 자동 재계산하지 않는다.
원문 전화번호, 대여 코드, 반출 인증 토큰은 성공 본문에 넣지 않는다.

## 5. 저장과 상태 전이

기존 구조를 재사용한다:

- V5 `rentals`: 대여자·물품·반출 시각·예정일을 저장하고 `status=RENTED`, `returned_at=NULL`로 생성한다.
- V7 `uq_active_rental_item`: `returned_at IS NULL`인 대여는 물품당 하나만 허용한다. 연체 상태도 진행 중 대여다.
- `ItemRepository.findForUpdate()`: 물품 행 잠금 안에서 존재·태그·상태·종류·진행 중 대여를 재검사한다.
- V12 `item_status_history`: `AVAILABLE → RENTED`, `source=RENTAL_FLOW`, `changed_by_user_id=인증된 대여자`를 저장한다.

권장 처리 순서는 인증 토큰 식별 → 연결 코드 잠금 → 동일 키 결과 확인 → 코드 유효성·미사용 확인 → 물품 잠금·검증 → 일괄 저장이다.
잠금 대기 후에도 만료 시각을 재검사한다. 대여 생성, 코드 소비 등 모든 관련 흐름의 잠금 순서를 맞춰야 한다.
같은 코드로 다른 물품을 동시에 요청해도 한 번만 반출된다. 같은 물품을 다른 사용자가 요청해도 한 번만 반출된다.
관리자 상태 변경과 반출은 같은 물품 행 잠금을 사용하므로 서로의 검사를 우회하지 않는다.
처리 중 실패하면 대여·물품·이력·코드 소비·성공 결과를 모두 롤백한다.

V13 `create_rental_authorization`에 대여 코드·반출 토큰·성공 결과·검증 횟수 테이블을 추가했다.
기존 V5~V12는 수정하지 않았다. 통합 시 다른 브랜치의 마이그레이션 번호 중복 여부를 확인한다.
기존 SMS `verification_grants`와 `auth_operations`를 대여 코드 저장소로 임의 재사용하지 않는다.

## 6. 오류와 재시도

기존 API와 같은 오류 형태를 사용한다.

```json
{
  "error": {
    "code": "ITEM_NOT_AVAILABLE",
    "message": "현재 반출할 수 없는 물품입니다.",
    "retryAt": null
  }
}
```

| HTTP | code | 조건 |
|---|---|---|
| 400 | `INVALID_INPUT` | JSON·ID·필수 멱등 키 형식 오류, 미정의 필드 |
| 401 | `RENTAL_GRANT_REQUIRED` | 반출 전용 토큰 누락 |
| 401 | `RENTAL_GRANT_INVALID` | 알 수 없거나 위조된 반출 토큰 |
| 410 | `RENTAL_GRANT_EXPIRED` | 토큰 또는 연결 코드 유효 시간 만료 |
| 403 | `FORBIDDEN` | 허용되지 않는 Origin 등 접근 거부 |
| 404 | `ITEM_NOT_FOUND` | 없는 물품 |
| 409 | `RENTAL_CODE_CONSUMED` | 이미 사용한 코드로 새로운 반출 시도 |
| 409 | `ITEM_TYPE_MISMATCH` | 선택한 종류와 물품의 현재 종류 불일치 |
| 409 | `ITEM_NOT_AVAILABLE` | AVAILABLE 아님 또는 태그 없음 |
| 409 | `RENTAL_ALREADY_ACTIVE` | 진행 중 대여 존재 또는 활성 대여 유니크 충돌 |
| 409 | `IDEMPOTENCY_KEY_CONFLICT` | 같은 인증 범위·키를 다른 본문에 사용 |
| 500 | `INTERNAL_ERROR` | 분류되지 않은 저장 실패. 세부 SQL·자격 정보는 응답하지 않음 |

인증을 먼저 검증한 뒤 물품 정보를 확인한다. 새 요청의 물품 오류 우선순위는 없음 → 종류 불일치 → 진행 중 대여 존재 → 반출 불가다.
알려진 활성 대여 유니크 충돌만 409로 변환하고, 다른 저장 오류를 중복 대여로 오인하지 않는다.

- 멱등 범위는 서버의 반출 인증 토큰 식별자 + 요청 키다. 키 자체는 인증 수단이 아니다.
- 같은 토큰·키·본문으로 성공 결과가 있으면 저장된 응답을 재생하며, 코드가 소비되었다는 이유로 이 재생을 막지 않는다.
- 같은 범위·키의 본문이 다르면 409다. 다른 키나 같은 코드의 다른 토큰을 이용한 새 요청은 이미 소비된 코드로 거부한다.
- 재생은 원래 반출 토큰의 만료 전까지만 허용한다. 만료 시 새 반출을 시도하지 말고 결과를 미확정으로 표시한다. 실패·미완료로 단정하지 않는다.
- 만료 이후 결과 확인은 후속 본인 대여 조회 또는 별도 인증된 결과 조회가 필요하다. 이번 계약은 존재하지 않는 결과 조회 API를 가정하지 않는다.
- 성공 결과와 본문 비교 정보는 DB에 보관하고, 적어도 재생 허용 기간 동안 유지한다. 프로세스 메모리만으로 중복 요청을 제어하지 않는다.
- 명확히 실패하여 롤백된 요청은 코드가 유효하면 재시도할 수 있다. 물품·종류를 바꾸면 새 작업 키를 사용한다.
- 키오스크는 응답을 받지 못한 경우 새 키로 반출을 반복하지 않는다. 사용 완료·취소·시간 초과 때 토큰을 제거한다.

`GET /api/tags/{uid}`는 `sms-mock` 개발 환경에서 반출 전용 토큰으로도 조회할 수 있다. `Authorization` 헤더가 없으면 기존 로그인 세션을 사용한다. 잘못된 반출 토큰은 세션 쿠키가 있어도 거부한다. 이 토큰으로 태그 변경이나 관리자 API를 호출할 수 없다. 조회 결과에는 `itemTypeId`가 없으므로, 키오스크가 선택한 종류와 반출 본문의 `itemTypeId`를 연결하는 방법은 프론트 통합에서 별도로 맞춰야 한다.

## 7. 구현 의존성과 1단계 체크

## 10. 4단계: HTTP API·인증·재시도 연결

- [x] 엄격한 문자열 ID 요청 DTO와 반출 Controller 추가
- [x] 서버 발급 반출 토큰 인증, 만료 재검사, Origin·입력·중복 헤더 검증
- [x] 없는 물품·종류 불일치·반출 불가·진행 중 대여·사용된 코드 오류 구분
- [x] 최초 201, 같은 토큰·키·요청 필드의 성공 결과 재생 200, 다른 필드는 409
- [x] 저장 후 대여 ID·물품 ID·종류 ID·반출 시각·예정일·대여/물품 상태 반환

`RentalController` → `RentalOperationService` → `RentalCheckoutService` 순서로 처리한다.
반출 인증 토큰을 서버에서 조회한 뒤 연결된 코드 행을 잠그고, 같은 요청 키 결과를 먼저 조회한다.
새 반출은 미사용 코드만 허용한다. 물품 잠금 대기 후 토큰이 만료되었으면 저장을 롤백한다.
대여·물품·상태 이력·코드 소비·멱등 결과 모두 동일한 DB 트랜잭션에 참여한다.
성공 결과는 `rental_operations`에 생성 당시 값을 보관하므로 이후 대여의 예정일이 변경되어도 재생 값은 유지된다.

코드 검증에 성공해도 코드를 소비하지 않는다. 같은 코드에서 나온 여러 토큰도 코드 행 잠금을 공유하므로
다른 물품에 동시에 사용해도 하나만 성공한다. 같은 토큰·키는 직렬화하여 기존 성공 결과를 반환한다.
별도 코드로 같은 물품을 요청하면 물품 행 잠금과 V7 인덱스로 중복 대여를 막는다.

코드 조회용 HMAC, 표시용 HMAC, SMS 용도는 문자열 접두어로 분리한다. 코드 표시값은 UUID와 서버 키로 재생성하고
DB에는 코드 평문을 저장하지 않는다. 토큰은 32바이트 난수이며 SHA-256 해시만 저장한다.
사용·만료된 코드의 조회 해시 예약을 해제하여 6자리 공간을 재사용한다. 과거 토큰·성공 결과는 원래 코드 ID와 연결된다.
개발 키는 기존 `sms-mock` 설정을 사용하므로 운영 프로필에서 신규 인증·반출 API를 활성화하지 않는다.

코드 발급·검증 추가 오류:

| HTTP | code | 조건 |
|---|---|---|
| 400 | `INVALID_INPUT` | 6자리 문자열 외 코드, 알 수 없는 필드 등 |
| 401 | `SESSION_REQUIRED` / `SESSION_EXPIRED` / `SESSION_REPLACED` | 코드 발급용 모바일 세션 없음·만료·교체 |
| 401 | `RENTAL_CODE_INVALID` | 알 수 없거나 만료·사용된 코드. 검증에서 이 사유들을 구분해 노출하지 않음 |
| 429 | `RENTAL_VERIFICATION_LIMITED` | 접속 주소별 또는 전체 검증 한도 초과, `retryAt` 제공 |
| 429 | `RENTAL_CODE_ISSUANCE_LIMITED` | 최근 1시간 사용자별 신규 발급 한도 초과 |
| 503 | `RENTAL_CODE_UNAVAILABLE` | 제한된 충돌 재시도 안에 코드를 확보하지 못함 |

반출 요청의 `Idempotency-Key`는 정규 UUID 형식을 요구하며 대소문자는 같은 UUID로 해석한다.
본문 비교는 검증된 `itemId`·`itemTypeId` 기준이므로 JSON 공백·필드 순서는 결과에 영향을 주지 않는다.
성공이 확인되지 않은 상태에서 토큰까지 만료되면 자동으로 새 코드·새 키로 반출하지 않는다.
만료 후 결과 조회와 프론트엔드 복구 UI는 다음 연동 범위다.

4단계 검증: 2026-10-14 `backend/scripts/test-item-postgres.ps1` 실행, 총 122개 통과
(실패·오류·건너뜀 0). 신규 HTTP/PostgreSQL 통합 15개와 인증 경계 2개, 기존 세션 인증 회귀 8개를 포함한다.

- 코드 발급·검증부터 실제 반출 저장까지 호출하고 성공 응답의 ID·시각·상태 확인
- 모바일 세션만으로 반출 불가, 위조·누락·만료 토큰, 인증 서비스 부재, 중복 헤더 거부
- 잘못된 JSON·숫자 ID·범위 초과·요청 userId/예정일 등 미정의 필드와 허용되지 않은 Origin 거부
- 같은 요청의 성공 재생, 기존 대여 변경 후에도 원래 성공 응답 유지, 같은 키의 다른 본문 충돌
- 같은 작업 동시 재전송, 같은 코드의 여러 토큰으로 다른 물품 반출, 다른 사용자의 같은 물품 반출 경합
- 멱등 결과 저장을 DB 제약으로 실패시켜 대여·물품·이력·코드 소비가 모두 롤백되고 같은 키로 재시도 가능한지 확인
- 잘못된 코드 시도도 DB 횟수에 반영, 임의 전달 헤더 우회 불가, 주소별·전체 검증 제한 및 사용자별 신규 발급 제한
- 만료된 코드 교체와 유효 코드 재표시, 원래 토큰 만료 시 성공 재생도 거부

MockMvc를 통한 서버 HTTP 처리와 실제 격리 PostgreSQL을 검증했다. 실행 중인 브라우저·실물 키오스크·NFC 장비나
운영 HTTPS·프록시 환경 검증은 아니다. 테스트 DB는 종료했고 운영 DB는 변경하지 않았다.
V13은 테스트 DB에 적용·검증했으며, 개발 서버 재시작 시 Flyway가 해당 환경에 적용한다.
