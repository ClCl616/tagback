# 기존 로컬 개발 DB 전환 기록

2026-11-19 `localhost:5432/tagback` PostgreSQL 17.11을 확인했다. 별도의 `tagback-kakao-auth-test` Docker DB나 운영 DB와는 다른 DB다.

## 백업과 적용

- 적용 전 Flyway 이력은 V1~V8, 실패 0건이었다. 사용자·물품 종류·물품·태그·대여·점검·SMS 3개 테이블·브라우저·세션·인증 작업의 정확한 행 수는 모두 0이었다. 행 수만으로 모든 가능한 외부 데이터나 백업의 성격을 판단하지 않는다.
- Git 제외 로컬 경로 `.local-backups/tagback-pre-kakao-20261119-175210.dump`에 `pg_dump` custom 형식 백업을 만들었다. 백업을 별도 PostgreSQL DB에 복원해 V8 이력과 사용자·물품·대여 행 수를 확인했다. 이 파일은 암호화된 외부 백업이 아니며 접근 권한과 보관 위치를 별도로 관리해야 한다.
- 복원본에서 Flyway가 V9~V23을 적용하고 Hibernate 스키마 검증을 통과했다. 기존 DB에 다른 접속이 없음을 확인하고 같은 V9~V23을 적용했다. V21·V22·V23의 성공과 `users.phone_number`의 NULL 허용, 주요 테이블의 행 수 0을 다시 확인했다.
- 기존 로컬 개발 DB의 확인한 테이블에는 초기화할 행이 없어 별도의 DELETE/TRUNCATE는 실행하지 않았다. 위 상태는 해당 시점의 이 DB에 한정된다. 격리된 카카오 시험 DB의 시험 계정은 별도로 보존 중이다.
- 다른 개발자 DB와 추후 운영 DB에는 적용하지 않았다. 적용 전 대상 식별, 실사용 데이터 포함 여부 확인, 백업·복원 검증과 서비스 중지 및 배포 순서를 각 환경에서 다시 확인한다.

## 전화번호·SMS 스키마 정리 범위

목표는 최종 사용자 인증에서 `users.phone_number`와 SMS 전용 `verification_grants`, `sms_verifications`, `sms_request_gates`를 제거하는 것이다. 실제 제거는 기존 데이터 전환·초기화 확인과 전체 인증·대여·반납 및 탈퇴 회귀 검증 이후에 별도 새 Flyway 버전으로 수행한다. V1~V23을 수정하지 않는다.

- 현재 `User` 엔티티와 `UserRepository`에 전화번호 필드·조회 경로가 남아 있고, 탈퇴 서비스는 기존 번호에 연결된 SMS 데이터를 삭제한다. 일부 기존 통합 테스트도 전화번호를 가진 사용자를 직접 생성한다. DB 칼럼·테이블만 제거하면 애플리케이션과 테스트가 실패한다.
- 외래 키는 `verification_grants` → `sms_verifications` → `sms_request_gates` 순으로 연결된다. 사용자와 대여·브라우저 등록·세션 등도 연결되어 있어 사용자 초기화 범위를 별도 확인해야 한다. 새 DB 버전의 정리 순서는 위 의존성과 실제 DB 카탈로그를 바탕으로 검증한다.
- 역사적인 V8 마이그레이션과 그 보존 테스트는 유지한다. 새 버전이 빈 DB와 V8/V23 기존 데이터가 있는 DB 모두에서 동작하는지, 보존할 데이터가 있을 때는 삭제되지 않거나 안전하게 중단되는지 검증한다.
- 아직 키오스크 실물 및 별도 브라우저를 포함한 전환 검증이 끝나지 않았고 다른 환경 데이터 상태도 확인하지 못했으므로, 파괴적인 스키마 삭제 마이그레이션은 아직 작성·적용하지 않았다.
