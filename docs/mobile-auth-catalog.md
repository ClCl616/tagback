## mock 문자 인증

`ServiceApi.requestSms(phone)`은 challenge ID·expiresAt·resendAt을 반환하고, `verifySms(id, phone, code)`는 가입용 proof를 반환한다. `signup(phone, password, verificationToken)`은 번호 일치·proof·유효시간·소비 여부를 다시 검사한다. proof 생략은 모의 API에서도 거부한다.

- 고정 시연 번호 `123456`, 유효시간 3분, 재요청 30초 대기, 오입력 최대 5회: `shared/config.ts`의 **임시 설정**.
- 요청 실패 후 재시도, 틀린 번호 수정, 만료/시도 초과 후 재요청, 중복 가입 오류를 표시한다.
- 재요청은 이전 challenge와 proof를 폐기한다. 입력 전화번호 변경 시 화면의 인증 상태를 초기화한다.
- proof는 인증번호와 같은 만료 시점을 사용하며 가입 성공 시 소비한다. 새로고침 시 입력과 인증 상태를 초기화한다.
- 처리 중 요청은 ref로 중복 방지한다. 화면을 떠난 뒤 도착한 응답은 화면과 로그인 상태를 변경하지 않는다.
- 실제 SMS는 발송하지 않는다. 고정 번호는 개발 시뮬레이터와 이 문서에만 시연값으로 제공한다.
- localStorage의 mock 인증 데이터는 보안 경계가 아니다. 운영 환경에서는 서버가 랜덤 OTP·발송 제한·검증·proof 소비·비밀번호 보호·인증 실패 제한을 책임진다.

## 물품 조회의 실제 API 전환

현재 M01/M02는 `ServiceApi.catalog()`의 mock 결과를 사용한다. 반환 타입은 `Catalog { stations, kinds, items }`이며 종류와 실물을 구분한다. 프론트엔드가 active 및 available 실물 수를 집계한다. 키오스크 변경 알림과 탭 포커스 복귀 시 재조회하며, 수동 새로고침도 제공한다.

HTTP URL·인증 헤더·페이지네이션·DTO는 백엔드와 추후 합의한다. 대용량 운영 재고는 서버의 집계 DTO로 변경할 수 있다. UI가 직접 fetch하거나 서버 경로를 추측하지 않는다. DB는 현재 단일 대여소로 station 테이블이 없으므로 HTTP adapter의 고정 대여소 매핑 또는 서버 반환 방식을 먼저 합의한다. 향후 여러 대여소가 추가되면 stations 결과로 선택 항목을 늘릴 수 있다.

## 기존 데이터

mock DB 키는 유지한다. 최초 조회 시 이전 데이터만 schemaVersion 2로 이관하여 계정과 대여 이력을 보존한다. 기존 다른 대여소 물품과 기록·저장 결과의 대여소 ID를 공학관으로 이관한다. 새 seed에는 계산기 009가 없지만 이전 데이터의 계산기 009는 유실 방지를 위해 보존한다. 따라서 기존 브라우저의 총 재고는 새 seed와 다를 수 있다. 초기화는 시뮬레이터에서 명시적으로 실행한다.

## 후속 연동

1. 백엔드와 로그인·SMS·가입 오류 코드 및 세션 계약 합의.
2. SMS 공급자·운영 인증 정책 확정 후 서버 발송 adapter 구현.
3. 목록/상세 조회 DTO와 단일 대여소 ID 매핑 합의 후 HTTP adapter 구현.
4. 실제 서버 인증·인가, 운영 데이터 및 실물 NFC로 별도 검증.
