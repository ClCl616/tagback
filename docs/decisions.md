## 현재 구현 기준 · 2026-10-18

- 모바일 회원가입: 이름·직업 → 전화번호 → SMS → 6자리 PIN. 기존 회원은 전화번호+PIN; 등록 브라우저는 PIN 로그인 지원.
- SMS는 개발용 mock이며 기본 재발송 간격 30초, 코드 5분. 운영 SMS 발송은 미연결.
- 키오스크는 별도 6자리 대여 코드(3분)로 인증한다. 반출 예정일은 서버 반출 시각부터 72시간이다. 운영 정책 확정과 구현 기본값은 구분한다.
- 현재 방향은 외장 리더기·키오스크이며 스마트폰 직접 NFC는 초기 계획이다. PR #20은 아직 develop 미병합이다.
- 태그 조회는 GET /api/tags/{uid}, 연결·교체·해제는 /api/items/{itemId}/tag. UID는 16진수 8/14/20자리로 정규화한다.
- 물품 상태는 TAG_PENDING / AVAILABLE / RENTED / INSPECTION / REPAIR. 대여 조회는 RENTED / OVERDUE / RETURNED를 사용한다.
- 예약·AI 손상 판정은 현재 MVP에서 제외한다. 태그 인식과 사용자 확정·서버 저장은 분리한다.

## 2026-10-06 사용자 확정 (당시 기록; SMS 재발송은 이후 30초로 변경)

전화번호·SMS·6자리 PIN으로 인증을 변경한다. PIN 패턴 금지, 5회 단위 단계 제한, SMS 5분/1분/5회, 로그인 성공 시 브라우저 자동 등록 및 단일 활성 등록, 로그아웃 시 등록 유지, 재설정 시 모든 인증 폐기를 적용한다. 운영 복구와 세션 TTL 등 미정 값은 [PIN 인증 문서](pin-auth.md)에 분리한다.

## 2026-10-06 인증 화면 피드백

사용자 지시에 따라 미등록 브라우저의 로그인도 전화번호와 PIN으로 처리한다. SMS는 가입·복구·번호 변경에서 유지한다. 브라우저 등록/단일 접속/PIN 제한은 그대로 적용한다. 전화번호 입력만으로 인증하거나 등록하지 않는다. 서비스 화면의 시연 설명은 제거하고 mock 여부는 개발 도구와 문서에 유지한다.

## 로그인 및 대여 코드 최신 정책
로그인 완료 후 next 요청과 관계없이 /mobile로 이동한다. 가입 완료의 기존 복귀 동선은 유지한다. 대여 코드 유효시간은 3분이며 코드 화면에서 만료 또는 사용 완료 시 자동 갱신한다. 조회/갱신 실패 시 오류와 재시도를 제공하며 무한 재요청하지 않는다. 기존 유효 코드의 잔여 시간도 최대 3분으로 한 번 보정한다.

## 2026-11-02 사용자 확정 (9주차 반납 기본 규칙)

- 대여자 본인이 키오스크에서 반납을 확정한다. 서버는 대여자 본인 여부를 검증하는 별도 반납 인증을 요구한다. 반출 때 소비된 대여 코드는 반납 인증에 재사용하지 않는다.
- 키오스크가 NFC로 읽은 `itemId`를 반납 대상으로 사용하고, 서버가 해당 물품의 진행 중 대여를 찾아 처리한다.
- 정상 반납 후 물품 상태는 `AVAILABLE`로 변경한다. 점검·수리가 필요한 물품은 별도 흐름에서 `INSPECTION` 또는 `REPAIR`로 처리한다.
- 반납 시각은 클라이언트 입력을 받지 않고 서버 시각으로 저장한다.

## 2026-11-02 9주차 반납 API 구현 기준

- 반납 API는 로그인 세션으로 대여자 본인을 확인하도록 개발 프로필에 구현했다. 공유 키오스크에 사용자 세션을 전달하지 않으며, NFC 결과를 세션 클라이언트에 안전하게 전달하는 연동과 운영 인증은 별도 작업이다.
- 후속 검증: 중복 반납 방지와 반납 API 계약을 검증한다. [물품 반납 API 계약](rental-return-api-contract.md)을 참조한다.

## 2026-11-03 반납 NFC 실물 확인 피드백 반영

- 물품 번호나 브라우저가 보낸 UID만으로 반납할 수 없다. ACR1552U 리더기 이벤트에 Java 브리지가 생성한 HMAC 서명을 포함하고, 서버가 공유 환경 비밀로 검증한다.
- 서버는 서명된 브리지 ID와 UID로 물품·진행 중 대여를 조회하고, 브리지 ID·UID·nonce·물품·대여에 묶인 60초짜리 임의 스캔 티켓을 발급한다. 브리지 서명 nonce는 티켓 발급 시 소비하며 최종 반납에서 동일한 서명 증명을 확인하고 티켓을 원자적으로 한 번만 소비한다.
- 최종 반납 요청은 물품 번호·UID·대여 ID를 입력값으로 받지 않는다. 서버 발급 티켓과 티켓 발급 때의 브리지 서명 증명, 상태 선택만 받는다. 프런트엔드에는 HMAC 비밀값을 두지 않는다.
- 11월 2일의 대여자 세션 검증 기준은 이 반납 흐름으로 대체한다. 실제 ACR1552U 환경 검증은 별도 기록한다.

## 2026-11-03 대리 반납 불허 결정

- 반납 순서는 태그 스캔 → 상태 선택 → 대여자 본인의 6자리 일회성 코드 입력 → 완료다.
- 서버가 코드 소유자와 스캔 티켓에 묶인 진행 중 대여의 대여자를 비교한다. 일치하지 않으면 반납을 저장하지 않는다.
- 대여·반납에 같은 코드 발급 체계를 사용하지만, 코드는 한 번만 소비한다. 이미 반출에 쓴 코드는 반납에 재사용할 수 없다. 응답 유실 재시도에는 소비된 바로 그 코드와 티켓·증명·상태를 요구한다.
