# 카카오톡 챗봇 인증 설계 초안

상태: 카카오 가입·새 브라우저 로그인·PIN 재설정의 서버와 프론트엔드를 구현했다. 2026-11-23 격리 시험 환경에서 실제 카카오톡을 이용해 주요 인증 흐름을 확인했다. 운영 환경 및 다른 팀원 노트북에서의 검증은 남아 있다. 확정된 사용자 정책은 [인증 정책](kakao-chatbot-auth-policy.md)을 따른다. 아래 2026-11-17의 채널 연결 해제 기록은 과거 시험 당시 상태이며 현재 상태를 뜻하지 않는다.

## 개발용 챌린지 구현 범위

- 개발용 `kakao-auth` 또는 명시적인 운영용 `kakao-live`와 `prod`/`production`에서 활성화된다. `tagback.kakao.hmac-key`, `tagback.kakao.skill-secret`은 서로 다른 32자 이상의 임의 비밀로, `tagback.kakao.bot-id`는 허용할 봇 ID로 설정해야 한다. 운영 설정과 검증 범위는 [운영 프로필 문서](kakao-live-profile.md)를 따른다.
- `POST /api/v1/auth/kakao/challenges`는 목적(`SIGNUP`, `LOGIN`, `PIN_RESET`)을 받고 10자리 무작위 코드와 요청 ID를 반환한다. 소유 증명은 별도의 Secure·HttpOnly·SameSite=Lax 쿠키다. 기본 유효시간은 300초이며 `tagback.kakao.code-ttl-seconds`로 30~600초 범위에서 조정할 수 있다. 같은 쿠키로 재발급하면 목적과 관계없이 이전 대기·인증 요청을 취소한다.
- `GET /api/v1/auth/kakao/challenges/{id}`와 `DELETE /api/v1/auth/kakao/challenges/{id}`는 해당 브라우저 증명을 요구한다. 스킬 `POST /api/v1/auth/kakao/skill`은 중복 없는 비밀 헤더, 예상 봇 ID, botUserKey와 10자리 발화를 확인하고 대기 요청을 인증 처리한다. 같은 사용자의 재전송은 성공으로 취급하며 다른 사용자는 같은 요청을 획득할 수 없다. 응답에는 인증 목적이나 식별값을 표시하지 않는다.
- 개발 기본 요청 제한은 1분당 발급 주소별 20회·브라우저별 5회, 스킬 전체 60회·주소별 30회·사용자별 5회다. 제한은 DB에서 원자적으로 계산한다. 역방향 프록시 환경에서는 서버가 받는 원격 주소가 공유될 수 있으므로 신뢰할 프록시 경계와 분산·우회 대응을 별도 설계해야 한다. 현재 값은 운영 정책으로 확정된 값이 아니다. 만료·제한 기록의 주기적 정리는 구현·격리 시험했으며 실제 사용할 서버 이미지에 반영하고 운영 보관 기간을 확정해야 한다.
- 개발용 `POST /api/v1/auth/kakao/signup`은 `challengeId`, `pin`, `profile`과 `Idempotency-Key` 헤더 및 챌린지 소유 쿠키를 받는다. 가입 목적·인증·만료·소유권을 재확인하고 계정·식별값·브라우저·세션 생성과 챌린지 소비를 한 트랜잭션으로 처리한다. 동일 식별값 동시 가입은 직렬화와 DB 고유 제약으로 방지하며 이미 가입한 식별값에는 `KAKAO_IDENTITY_ALREADY_REGISTERED`를 반환한다. 같은 브라우저에서 동일 키와 요청으로 유효 기간 안에 재시도하면 기존 결과와 쿠키를 반환한다.
- 개발용 `POST /api/v1/auth/kakao/login/new-browser`는 `challengeId`, `pin`, `Idempotency-Key` 헤더와 챌린지 소유 쿠키를 받는다. 로그인 목적·소유권·인증·만료 상태와 연결된 계정을 확인하고 기존 PIN 실패 제한을 적용한다. 성공 시 인증을 소비하고 이전 브라우저와 세션을 폐기한 뒤 새 등록과 세션을 생성한다. PIN 실패나 저장 오류는 기존 접근을 유지하며, 같은 브라우저의 동일 키·요청 재시도를 처리한다.
- 개발용 `POST /api/v1/auth/kakao/pin/reset`은 `challengeId`, 새 `pin`, `Idempotency-Key` 헤더와 챌린지 소유 쿠키를 받는다. PIN 재설정 목적·소유권·인증·만료 상태와 연결된 계정을 확인하고 요청을 소비한다. PIN 변경과 실패 횟수 초기화, 기존 세션·브라우저 폐기를 한 트랜잭션으로 처리한다. 같은 브라우저의 동일 키·요청을 유효 기간 안에 재시도하면 기존 완료 결과를 반환하고, 이후 새로 발급된 인증 쿠키를 지우지 않는다.
- 프론트엔드와 실제 카카오톡을 이용한 격리 시험은 진행했다. 운영 배포와 실제 NFC 장비를 포함한 전체 종단 시험은 아직 진행하지 않았다.
- 격리된 PostgreSQL에서 카카오 형식의 스킬 요청을 HTTP로 보내 가입 → 새 브라우저 로그인 → PIN 재설정 → 새 PIN 로그인까지 통합 테스트했다. 인증 목적 혼용 6가지, 각 최종 요청의 중복 소비와 응답 유실 재시도, PIN 불일치, 세션 교체·폐기, 취소·만료 및 비밀 헤더 누락을 함께 확인했다. 실제 카카오 서버 또는 프론트엔드를 통한 종단 시험은 아니다.

## 데이터 구조 및 기존 데이터 방침 (2026-11-17)

- `V21`은 기존 사용자와 SMS 데이터를 삭제하거나 카카오 식별값에 자동 연결하지 않는다. 팀에서 기존 데이터가 개발용임을 확인했고 **개발 중 보존 후 초기화**하기로 정했다. 카카오 가입·로그인·PIN 재설정과 대여 회귀 검증이 끝나고 실사용 데이터 투입 전 초기화 대상을 식별해 팀이 별도로 실행한다. 기존 테스트 계정은 이관하지 않고 카카오 인증으로 새로 가입한다. 대여 등 외래 키와 테스트 환경 및 백업·내보내기 파일을 확인하고, 실사용 데이터가 섞여 있으면 일괄 초기화를 중단해 보존·이관을 다시 결정한다. 이 문서는 데이터 삭제를 실행하지 않는다.
- `users.phone_number`의 DB NOT NULL 제약을 해제했다. 카카오 가입 API는 전화번호 없이 계정을 생성하며 SMS 가입·로그인 기능은 제거했다. 기존 데이터와 전화번호 고유 제약은 유지한다.
- 카카오 인증 가입은 전화번호 없이 사용자를 생성한다. 로그인·세션·브라우저 상태 응답은 전화번호를 반환하지 않는다. 키오스크 대여 인증 응답은 이름과 회원번호를 반환하여 동명이인을 구분한다. 이름이 없는 기존 계정은 `회원`과 회원번호로 표시한다.
- `kakao_bot_identities`는 계정당 연결 한 개, `(bot_id, bot_user_key)`당 계정 한 개를 강제한다. botUserKey는 봇에 종속되므로 봇 변경 시 별도 연결 절차가 필요하며 서로 다른 봇의 사용자를 동일인으로 간주하지 않는다. 원문 식별값은 접근을 제한해야 한다.
- `kakao_auth_challenges`는 목적, 상태, 만료, 인증·소비 시각, 일회용 코드 HMAC, 별도 브라우저 소유 증명 HMAC과 인증된 봇 식별값을 저장한다. 원문 코드와 브라우저 비밀을 저장하지 않는다. HMAC 키의 비밀 저장, 도메인 분리, 키 회전 및 만료 행 정리는 API 구현 시 필요하다. DB 제약은 조건부 갱신·잠금, 브라우저 소유 확인, 요청 제한을 대체하지 않는다.
- 카카오톡에서 한 계정으로 연속 두 번 보낸 요청은 같은 `user.id`를 반환했고, `botUserKey`와 `plusfriendUserKey`가 있었으며 `appUserId`는 없었다. 두 계정 간 비교, 장기 유지, 봇·채널 변경 및 차단·재추가 시의 동작은 확인되지 않았다. 자세한 시험과 현재 채널 상태는 [스킬 연결 문서](kakao-skill-access.md)를 따른다.
- 카카오 [스킬 요청 형식](https://kakaobusiness.gitbook.io/main/tool/chatbot/skill_guide/answer_json_format)은 `user.id`를 봇별 사용자 키로 설명하며, 같은 사용자라도 봇이 다르면 다른 ID가 발급된다고 명시한다. 카카오 [개발자 답변](https://devtalk.kakao.com/t/rest-api-appuserid/145889)은 `appUserId`가 항상 전달되지 않으므로 필수 식별자로 취급할 수 없다고 설명한다. 2021년 [개발자 답변](https://devtalk.kakao.com/t/botuserkey/115201)은 연결 해제 후 다시 친구를 맺을 때 새 키가 생성될 수 있다고 하면서 챗봇 담당자에게 확인을 권한다. 이 오래된 답변을 현재의 확정 정책으로 취급하지 않는다.
- 차단 후 재추가의 현재 동작을 시험하려고 채널을 일시 공개했지만, 동일 마스터 계정임에도 운영 채널 선택 목록이 비어 있어 기존 봇을 재연결하지 못했다. 리스트 메뉴 OFF 및 자동응답 0개를 확인했으며 원인은 확인되지 않았다. 차단 시험은 수행하지 않았고 채널은 다시 비공개, 서버와 터널은 중지했다.
- 운영 전 [카카오 챗봇 고객센터](https://cs.kakao.com/requests?service=169)에 `botUserKey`의 차단·해제·재추가, 채팅방 퇴장, 채널 재연결·변경, 카카오 계정 탈퇴·재가입 및 장기 보존 조건을 확인한다. 키가 변경될 수 있으므로 이 값만으로 영구적인 계정 복구나 사람당 한 계정을 보장하지 않는다. 봇 변경 시 기존 계정과 새로운 식별값을 안전하게 연결하는 별도 절차가 필요하다.

## 목표와 전제

- 가입, 새 브라우저 로그인, PIN 재설정 시 챗봇 인증을 사용한다. 등록 브라우저는 기존 PIN 방식으로 로그인한다.
- 전화번호를 수집하지 않고 1인 1계정을 목표로 하되, 같은 봇의 챗봇 사용자 식별값당 활성 계정 하나를 허용한다. 한 사람이 여러 카카오 계정을 사용하는 경우의 동일인 판별은 범위에서 제외한다.
- 카카오톡을 사용할 수 없거나 계정을 잃은 경우의 복구는 이번 범위에서 제외한다.
- 식별값 종류·수명·채널 변경 시 동작은 실제 채널 연동으로 검증하기 전까지 확정하지 않는다. `appUserId`가 항상 제공된다고 가정하지 않는다.

## 현재 코드의 변경 경계

1. DB의 `users.phone_number`는 선택 사항이지만 고유하다. 기존 데이터와 이전 마이그레이션을 보존하고 카카오 인증 API는 전화번호 없이 계정을 생성·조회한다.
2. 세션·브라우저 응답에는 전화번호 필드가 없고 키오스크 대여 grant는 `userName`과 `userId`를 사용한다. 서버·웹·Windows 호스트를 함께 배포해야 한다.
3. 공통 PIN·세션·대여 기능은 카카오 개발 또는 명시적인 운영 프로필에서 사용한다. 공통 비밀 `tagback.auth.common-hash-key`가 필요하며 환경 전환 시 기존 코드 및 멱등성 재시도에 미치는 영향을 검토한다. SMS mock API와 서비스는 제거했다.
4. `PinService`, PIN 실패 제한, 세션 및 브라우저 등록, 멱등성 처리의 기존 검증을 확인하며 재사용한다. 실제 운영 적합성은 별도 검증한다.

## 챌린지 흐름

1. 브라우저가 `SIGNUP`, `LOGIN`, `PIN_RESET` 중 하나를 지정해 챌린지를 생성한다. 서버는 예측 불가능한 일회용 코드와 무작위 챌린지 ID를 발급하고, 별도의 브라우저 소유 증명을 생성한다.
2. 사용자는 코드를 공식 TagBack 채널에 직접 입력한다. 코드를 받은 사람이 인증을 연결할 수 있으므로 타인에게 공유하지 않도록 안내한다. 코드는 전달·피싱을 완전히 막지 못한다.
3. 카카오 스킬 요청은 서버 간 HTTPS 경로에서 설정된 비밀 헤더를 검증한다. 브라우저의 Origin 검사나 챗봇 ID 문자열만으로 카카오 요청을 신뢰하지 않는다. 헤더 기능·비밀 관리·회전은 실제 설정에서 확인한다.
4. 서버는 코드의 유효성, 만료·취소·사용 여부를 원자적으로 확인한 뒤 챗봇 사용자 식별값을 해당 챌린지에 연결한다. 식별값을 브라우저가 직접 제출하게 하지 않는다.
5. 같은 브라우저가 챌린지 ID와 별도 소유 증명으로 완료 여부를 조회한다. ID나 코드는 소유 증명의 대체물이 아니다. 인증 결과는 원래 목적과 해당 브라우저에 결합한다.
6. 가입·로그인·PIN 재설정의 최종 요청에서 목적·브라우저 증명·만료·사용 여부를 다시 검증해 한 번만 소비한다. 새 브라우저 로그인에서는 PIN까지 성공한 후 기존 등록·세션을 폐기한다.

## API 초안

챌린지·스킬과 카카오 가입·새 브라우저 로그인·PIN 재설정 경로는 개발용으로 구현했다.

| 요청 | 역할 | 접근 조건 |
| --- | --- | --- |
| `POST /api/v1/auth/kakao/challenges` | 목적별 일회용 챌린지 생성 | 브라우저 Origin 검사·요청 제한 |
| `GET /api/v1/auth/kakao/challenges/{id}` | 대기·완료·만료 상태 확인 | 최초 브라우저 소유 증명 필수, `Cache-Control: no-store` |
| `DELETE /api/v1/auth/kakao/challenges/{id}` | 사용자의 미완료 요청 취소 | 최초 브라우저 소유 증명 및 Origin 검사 |
| `POST /api/v1/auth/kakao/skill` | 카카오 스킬 요청과 코드 처리 | 서버 간 비밀 헤더 검증 및 요청 제한 |
| `POST /api/v1/auth/kakao/signup` | 카카오 인증된 가입 완료 | 가입용 결과·브라우저 증명·PIN, 멱등성 적용 |
| `POST /api/v1/auth/kakao/login/new-browser` | 인증된 새 브라우저 로그인 | 로그인용 결과·브라우저 증명·PIN, 멱등성 적용 |
| `POST /api/v1/auth/kakao/pin/reset` | 인증된 PIN 재설정 | 재설정용 결과·브라우저 증명·새 PIN, 멱등성 적용 |

브라우저 증명은 서버가 발급한 고엔트로피 비밀값으로 설계한다. HttpOnly·Secure 쿠키 활용과 다중 탭·동시 요청·새로고침·SameSite 동작을 구현 시 검증한다. 조회의 인증 상태만으로 최종 작업이 완료된 것으로 표시하지 않는다.

## 상태와 동시성

- 챌린지 상태: `PENDING → VERIFIED → CONSUMED`; 대기·인증 상태는 취소되거나 만료될 수 있다. 코드 제출의 성공 자체는 회원가입이 아니다.
- 원문 코드·소유 증명·식별값을 로그에 남기지 않는다. 일회용 코드 저장에는 서버 비밀을 사용하는 HMAC 등 추측 저항 방식을 적용하고, 식별값 저장은 필요한 접근·삭제 정책과 함께 설계한다.
- 일치하지 않는 코드는 특정 챌린지를 안전하게 식별할 수 없으므로, 존재하지 않는 코드의 실패 횟수를 임의 챌린지에 귀속하지 않는다. 요청 출처·챗봇 식별값 등의 다층 제한과 코드 공간·유효기간을 함께 설계한다.
- 동일 코드 동시 제출, 여러 챌린지로 동일 식별값 가입, 인증 결과 동시 소비를 DB 잠금·고유 제약과 트랜잭션으로 검증한다.
- 카카오 스킬 재시도와 최종 요청 응답 유실을 고려한다. 멱등성 키가 같고 요청이 동일하면 결과를 안전하게 재확인하며, 서로 다른 요청을 같은 키로 재사용하면 거절한다. 비밀값과 PIN은 재시도 로그에 남기지 않는다.
- 코드 유효시간·시도 제한·재발급 간격은 미확정이다. 기존 SMS 값인 5분·5회·30초는 참고안이며 챗봇에 그대로 확정하지 않는다.

## 전환 및 테스트

- 기존 계정 이관은 데이터 보존 여부와 본인 확인 수단이 정해질 때까지 별도 설계한다. 이름이나 전화번호의 일치만으로 카카오 식별값을 자동 연결하지 않는다.
- 탈퇴는 미반납 대여가 있으면 거부하고, 탈퇴 후 같은 챗봇 식별값의 재가입을 허용한다. 반납 완료 이력은 사용자 식별 및 계정 연결을 제거하고 날짜를 일 단위로 줄여 탈퇴일부터 1년간 필요한 범위에서 보관한 뒤 삭제한다. 재가입 계정과 연결하지 않으며 재식별 위험과 법령상 별도 보존 필요성을 검토한다. 기존 사용자 외래 키, 로그·백업 및 복원 시 삭제 재적용도 설계한다.
- 스킬 요청 위조·재생, 코드 만료·취소, 목적 혼용, 다른 브라우저 조회, 중복 가입 경쟁, PIN 잠금, 기존 세션 유지·교체, 응답 유실 재시도를 테스트한다.
- 실제 카카오 채널에서 식별값, 스킬 헤더·요청 형식, 사용자 입력 전달, 타임아웃 및 공개 HTTPS 연결을 확인한다. 스킬 URL이 정해지기 전 가짜 운영 URL이나 비밀값을 등록하지 않는다.
- SMS mock 프로필이 외부에 노출되지 않는지와 관리자·키오스크·대여·반납 회귀를 별도 검증한다.
